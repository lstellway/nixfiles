## Jurisdictional and Temporal Caveats

- **Take rate guidance** is based on market data through 2023; public marketplace multiples and category averages shift with macro conditions. Anchor to stated sources rather than the specific numbers when precision matters.
- **Regulatory content** (marketplace facilitator tax laws, money transmission, occupational licensing) varies by US state and is evolving in most jurisdictions. The agent directs users to provide state/locale before answering regulatory questions; answers in those sub-domains should be verified against current state statutes.
- **NFX content** is periodically revised. The Network Effects Bible and Manual are "living" documents; specific wording and type counts may differ from print/cached versions.
- **Cold Start Problem book** published 2021. Network effect dynamics in specific categories (crypto, AI-native platforms) have developed substantially since publication; treat as foundational theory, not current-state market analysis.

## Design Notes

### Pattern: Consultation-led with deep vocabulary sections

Marketplace agents are most useful when the vocabulary sections are dense enough that the agent can answer "what's the difference between X and Y" directly — without web lookups — for the core 30–40 terms. The tradeoff is prompt size; acceptable here because the knowledge is stable and substantive.

### Pattern: Heuristics as conditional rules, not labels

The 9 heuristics in this agent are structured as `if <condition>, then <action>, because <mechanism>`. This is the pattern worth replicating in other domain agents. Heuristics that say "consider X" or "evaluate Y" are not heuristics — they are topic labels that give the user no decision support.

### Pattern: Bidirectional scope boundaries with capability references

Each boundary clause in the Scope section specifies both what stays here AND what defers to the peer, using capability/role descriptions rather than agent names. This pattern ensures boundaries are navigable even as the agent roster changes. Example: "stay here for trust as marketplace design; defer to a trust-safety specialist for fraud detection" — both directions, capability form.

### Pattern: Fintech as strategy, not implementation

The agent covers fintech integration as a marketplace strategy decision (why and when), explicitly deferring implementation and compliance to a fintech specialist. This two-agent split is cleaner than combining them — the strategic question (should we embed financial products?) is separate from the implementation question (how do we build and comply?). This split pattern is applicable to other domain + engineering pairs.

### Observed gap: No community marketplace strategy agent exists

VoltAgent/awesome-claude-code-subagents has no business strategy agents for marketplace dynamics. The closest entries are engineering-focused or generic. There is likely value in companion agents for: trust-and-safety design (distinct from fraud engineering), marketplace pricing (take rate optimization more specifically), and B2B marketplace strategy as its own agent given the significantly different dynamics (patient capital, demand-first, broker enablement, 5–8 year timeline).
